HackTheBox - ZaZamarin: Unboxing a .NET MAUI Android CTF Through Native Emulation

2026-09-15 / 14 min read / @uziii2208

Challenge: ZaZamarin
Category: Reverse Engineering (Mobile / .NET MAUI / Native C / Custom VM / Cryptography)
Platform: HackTheBox
Difficulty: Hard
Captured Flag: HTB{redacted}

1. Challenge Overview & Scenario Analysis

The challenge description provides crucial narrative clues:

"The app promised a reward. Six years, zero rewards. The company that built it is long gone, the framework it used changed names twice, and the only thing the original developer ever said about the 'unbreakable protection' was a laughing emoji. My grandfather still taps that button every morning before coffee. Today he tapped it and told me: 'someone will claim it one day; probably a n00bie.'"

Three primary technical insights emerge from this lore:

  1. "The framework it used changed names twice": References the lineage: MonoTouch/MonoDroid $\rightarrow$ Xamarin $\rightarrow$ .NET MAUI.
  2. "Taps that button every morning": The user interface features a single action button (Claim Reward) triggering the validation routine.
  3. "Unbreakable protection": Multi-layered defense including anti-debugging, anti-Frida, custom hashing, dynamic bytecode decryption, and a custom virtual machine.

2. APK Reconnaissance & Environment Architecture

Two critical artifacts immediately stand out:

  1. assets/vault.dat: Exactly 4096 bytes of pseudo-random binary data.
  2. libassemblies.<arch>.blob.so: A non-standard shared library storing .NET assemblies.

2.2 The Evolution of Xamarin to .NET MAUI Architecture

In older Xamarin applications:

  • Assemblies were packaged either as raw .dll files in assemblies/ or compressed via LZ4 (assemblies.blob accompanied by assemblies.manifest).
  • Tools like pyxamstore could directly decompress assemblies.blob.

In modern .NET MAUI (specifically .NET 9 for Android):

  • Assemblies are compiled and bundled directly inside an ELF shared object (libassemblies.<arch>.blob.so).
  • The bundle is stored inside a dedicated ELF section named payload.
  • Standard tools expecting .dll files in the APK fail completely.

2.3 Demystifying the XABA Assembly Store

Inspecting the payload section of libassemblies.x86_64.blob.so with Python:

with open('libassemblies.x86_64.blob.so', 'rb') as f:
    f.seek(0x4000) # Offset of 'payload' section
    header = f.read(32)

The header layout follows the XABA format:

Offset Field Value Meaning
0x00 - 0x03 Magic 58 41 42 41 ASCII string "XABA"
0x04 - 0x05 Version 02 00 Format Version 2
0x06 - 0x07 Flags 03 80 Assembly store descriptor flags
0x08 - 0x0B Count 7A 00 00 00 122 assemblies bundled in the store
0x0C - 0x0F Index Size F4 00 00 00 Index table entries

Each index entry defines:

  • Hash of assembly name
  • Offset to assembly data in the blob
  • Compressed length & uncompressed length
  • Name table index

4.3 Defensive Instrumentation: FridaDetector

The application runs periodic background checks every 2 seconds via IDispatcherTimer:

  1. CheckProcMapsForFrida(): Reads /proc/self/maps scanning for the string "frida".
  2. CheckEnvironmentVariables(): Inspects FRIDA, LD_PRELOAD, and DYLD_INSERT_LIBRARIES.
  3. CheckPtrace(): Inspects /proc/self/status for TracerPid != 0.
  4. CheckFridaTcpPort(): Attempts a TCP connection to 127.0.0.1:27042.
  5. CheckListeningOnLoopback(): Attempts a TCP connection to 127.0.0.1:27043.

If any check triggers:

4.4 Integrity Verification: BlobReader

Before triggering validation, BlobReader.ComputeBlobWord() calculates a dynamic checksum:

public static uint ComputeBlobWord()
{
    byte[] array = ReadBlobSlice();
    uint num = 2166136261u; // FNV-1a 32-bit offset basis
    foreach (byte b in array)
    {
        num ^= b;
        num *= 16777619;    // FNV-1a 32-bit prime
    }
    return num;
}

ReadBlobSlice() operates as follows:

  1. Obtains the APK path via ApplicationInfo.SourceDir.
  2. Opens the APK archive and resolves lib/{abi}/libassemblies.{abi}.blob.so.
  3. Skips the first 8,192 bytes (skipping ELF headers).
  4. Reads the subsequent 65,536 bytes (64 KB).
  5. Computes standard 32-bit FNV-1a:
    • For x86_64: blobWord = 0x8bdaee2f
    • For arm64-v8a: blobWord = 0xbdfd7043

This binds the execution integrity directly to the physical binary bits of the assembly store.

4.5 The Core Orchestrator: ChainRunner

When the user taps "Claim Reward", ChainRunner.ClaimCoreAsync() runs:

private static async Task<bool> ClaimCoreAsync()
{
    // 1. Read vault.dat
    byte[] vault = ... Read assets/vault.dat ...; // 4096 bytes
    uint blobWord = BlobReader.ComputeBlobWord();
    
    // 2. Step 1: Native Seed & Settle
    uint[] cells = new uint[64];
    if (Native_SeedAndSettle(vault, vault.Length, blobWord, cells) != 0)
        return false;
        
    // 3. Step 2: Managed Transform M1
    cells = M1(cells);
    
    // 4. Step 3: Native Unseal Program
    byte[] programBuf = new byte[1024];
    int progLen = programBuf.Length;
    if (Native_UnsealProgram(cells, programBuf, ref progLen) != 0)
        return false;
        
    byte[] unsealedProg = new byte[progLen];
    Array.Copy(programBuf, unsealedProg, progLen);
    
    // 5. Step 4: Managed Transform M2
    byte[] mangledProg = M2(unsealedProg, cells);
    
    // 6. Step 5: Native Run Program
    if (Native_RunProgram(mangledProg, mangledProg.Length, cells) != 0)
        return false;
        
    // 7. Step 6: Native Final Open
    return Native_FinalOpen() == 0;
}

This 6-step alternating state machine forms the complete cryptographic pipeline.

5. Native Library Deep-Dive (libflagnative.so)

5.1 ELF Symbol & Relocation Mapping

  - Native_FinalOpen      (0x2940, size 1158)
  - flag_commit           (0x2dd0, size 281)

5.2 Anti-Analysis & Native Sentinel Mechanisms

All native functions (Native_SeedAndSettle, Native_UnsealProgram, Native_RunProgram, Native_FinalOpen) execute inline anti-debugging checks:

  • Inspect /proc/self/maps for "frida", "gadget", "gum".
  • Inspect /proc/self/status for "TracerPid:".
  • Create AF_INET sockets and attempt TCP connections to 127.0.0.1:27042 and 127.0.0.1:27043.

If any check passes (meaning a debugger or Frida is detected):

  • A global sentinel variable at .bss + 0x00 (0xc960) is set to 1:
    0x1848: cmp dword ptr [rip + 0xb111], 0  ; [0xc960]
0x1851: mov dword ptr [rip + 0xb105], 1  ; [0xc960] = 1
  • If [0xc960] != 0, the native routines corrupt the state cells by XORing them with a garbage pattern (0xd5, 0x3c, 0x62 sequence), causing subsequent cryptographic operations to fail.

5.3 Stage 1: Native_SeedAndSettle & Cellular Mixing

Native_SeedAndSettle accepts (vault, vaultLen, blobWord, outCells):

  1. Absorbs vault.dat into 64 words using FNV/Murmur operations in sub-function 0x3580:
    edx = blobWord ^ 0x811c9dc5;
for (int i = 0; i < 64; i++) {
    uint r9 = edx;
    for (int off = 0; off < vaultLen; off += 2) {
        uint b0 = vault[off] + i;
        r9 = ((b0 ^ r9) * 0x1000193);
        uint b1 = vault[off + 1] + i;
        r9 = (r9 >> 11) ^ ((b1 ^ r9) * 0x1000193);
        r9 = (r9 >> 11) ^ r9;
    }
    cells[i] = r9;
}
  2. Passes cells into 0x3650, executing 4,096 rounds of a cellular automaton network:
    uint r8 = 0;
for (int round = 0; round < 4096; round++) {
    int rot1 = ((7 * round) & 15) + 1;
    int rot2 = ((11 * round) & 15) + 1;
    int rot3 = ((round >> 3) & 15) + 1;
    for (int i = 0; i < 64; i++) {
        uint prev = in[(i - 1) & 63];
        uint curr = in[i];
        uint next = in[(i + 1) & 63];
        uint m = curr ^ rotl(prev, rot1) ^ rotr(next, rot2);
        uint t = (m * 0x85ebca77) + r8 + i;
        t ^= (t >> 15);
        uint out = rotl(curr, rot3) ^ (t * 0xc2b2ae3d);
        out ^= (out >> 16);
        next_in[i] = out;
    }
    r8 += 0x9e3779b9; // Golden ratio constant
    swap(in, next_in);
}

5.4 Stage 2: Managed Transform M1

In C#, ChainRunner.M1 executes 5 bi-directional mixing passes:

public static uint[] M1(uint[] cells)
{
    uint[] array = new uint[64];
    Array.Copy(cells, array, 64);
    for (int i = 0; i < 5; i++)
    {
        bool flag = i % 2 == 0;
        for (int j = 0; j < 64; j++)
        {
            int num = flag ? j : (63 - j);
            uint x = array[(num - 1) & 0x3F];
            uint num2 = array[num];
            uint x2 = array[(num + 1) & 0x3F];
            uint num3 = num2 + Rotl32(x, 7) + Rotr32(x2, 17);
            num3 *= 2246822507u;
            array[num] = Rotl32(num3, 13);
        }
    }
    return array;
}

5.5 Stage 3: Native_UnsealProgram & AES-256-GCM Unsealing

Native_UnsealProgram takes the M1-churned cells:

  1. Calls 0x3880(cells, outKey): Hashes the 64 state cells into a 32-byte (256-bit) AES key.
  2. Calls 0x3980 (an inlined implementation of AES-256-GCM authenticated decryption):
    • Key: Derived 32-byte key
    • Nonce / IV: 12 bytes at .rodata + 0x8f4
    • Tag: 16 bytes at .rodata + 0x900
    • Ciphertext: 212 bytes (0xd4) at .rodata + 0x930
  3. Decrypts and verifies the 212-byte binary payload (the unsealed program).

5.6 Stage 4: Managed Keystream Permutation M2

In C#, ChainRunner.M2 generates a stream cipher keystream using AdvanceKeystreamBlock:

public static byte[] M2(byte[] program, uint[] cellsChurned)
{
    uint[] state = new uint[64];
    Array.Copy(cellsChurned, state, 64);
    byte[] result = new byte[program.Length];
    byte[] block = new byte[256];
    int offset = 0, blockIndex = 0;
    while (offset < program.Length)
    {
        AdvanceKeystreamBlock(state, blockIndex++, block);
        int take = Math.Min(256, program.Length - offset);
        for (int i = 0; i < take; i++)
            result[offset + i] = (byte)(program[offset + i] ^ block[i]);
        offset += take;
    }
    return result;
}

This XORs the 212-byte unsealed program with the keystream.

5.7 Stage 5: Native_RunProgram & Custom VM Disassembly

Native_RunProgram takes (mangledProgram, 212, cells):

  1. Recomputes the exact same keystream from cells (lines 0x241c to 0x24eb) and XORs it against mangledProgram. $$\text{Program} = \text{M2}(\text{Program}) \oplus \text{Keystream} = \text{Original Unsealed Bytecode}$$
  2. Clears the 32-byte master key buffer in .bss (0xc964 to 0xc983).
  3. Invokes the virtual machine interpreter at 0x4110:
    0x2738: lea rdi, [rsp + 0x100]  ; Decoded 212-byte bytecode
0x2740: lea rdx, [rsp + 0x600]  ; State cells (64 words)
0x2748: mov esi, 0xd4           ; Bytecode length (212)
0x274d: mov ecx, 0xf42400       ; Fuel limit (16,000,000 cycles)
0x2752: call 0x4110             ; VM Execution

The Custom Virtual Machine (Function 0x4110)

  • Architecture: Fixed 4-byte instruction length (uint32):
    • Byte 0: Opcode index
    • Byte 1: Operand / Register index
    • Byte 2: Register index / Offset
    • Byte 3: Immediate / Register index
  • Registers: 8 general-purpose 32-bit registers stored on stack (rsp + 0x110 to rsp + 0x12c).
  • Memory Map: State cells mapped to virtual memory space.
  • Dispatch: An indirect jump table indexed by opcode byte:
    0x4413: movsxd rsi, dword ptr [r12 + rsi*4]
0x4417: add    rsi, r12
0x441a: jmp    rsi
  • Goal of the Bytecode: The 212-byte program executes mathematical permutations over the state cells and writes the derived 32-byte Master AES Key directly into 0xc964 (.bss).

5.8 Stage 6: Native_FinalOpen & Flag Decryption

Native_FinalOpen executes the final phase:

  1. Verifies anti-debugging: ensures [0xc960] == 0.
  2. Sets up parameters for AES-256-GCM (0x3980):
    0x2cac: lea r10, [rip - 0x2393] ; Tag (16 bytes) at .rodata + 0x920
0x2cb3: lea rdi, [rip + 0x9caa] ; Master AES Key (32 bytes) at .bss + 0xc964
0x2cba: lea rsi, [rip - 0x23b1] ; Nonce / IV (12 bytes) at .rodata + 0x910
0x2cc1: lea rdx, [rip - 0x1f98] ; Ciphertext (41 bytes) at .rodata + 0xd30
0x2cc8: mov ecx, 0x29          ; Length = 41 bytes (0x29)
0x2ccd: xor r8d, r8d           ; AAD = NULL
0x2cd0: xor r9d, r9d           ; AAD len = 0
0x2cd3: push rax               ; Plaintext destination buffer on stack (rsp)
0x2cd4: push r10               ; Tag pointer
0x2cd6: call 0x3980            ; AES-256-GCM Decrypt
  3. If decryption succeeds (eax == 0), it calls flag_commit(rsp, 41):
    0x2cea: mov rdi, rsp           ; Pointer to plaintext flag
0x2ced: mov esi, 0x29          ; Length: 41
0x2cf2: call flag_commit
  4. flag_commit writes the flag into .bss + 0xc984, and immediately overwrites it with zeroes before returning.

6. Developing the Automated Solver via Unicorn CPU Emulation

6.1 Why CPU Emulation Over On-Device Dynamic Hooking?

Attempting to run the app on an Android emulator or device with Frida/Frida-gadget encounters multiple friction points:

  1. Frida is actively detected via ports 27042/27043, maps, and TracerPid.
  2. Android x86/ARM translation layers introduce latency and ABI mismatches.
  3. Modifying APK files requires repackaging, aligning, and re-signing, which breaks the BlobReader integrity hash.

CPU Emulation using Unicorn solves all these issues:

  • Runs headless on any operating system in pure Python.
  • Fast execution ($\sim 5$ seconds).
  • Complete, transparent control over CPU registers, memory, and PLT imports.
  • Anti-analysis checks can be trivially spoofed by returning clean mock values.

6.2 Setting Up the x86_64 Virtual Machine

from unicorn import *
from unicorn.x86_const import *

uc = Uc(UC_ARCH_X86, UC_MODE_64)

BASE = 0x400000
# Map Text + Rodata (RX)
uc.mem_map(BASE, 0x5000, UC_PROT_ALL)
# Map Data + GOT + BSS (RW)
uc.mem_map(BASE + 0x8000, 0x6000, UC_PROT_ALL)
# Map Stack (RW)
STACK_BASE = 0x700000
uc.mem_map(STACK_BASE, 0x80000, UC_PROT_ALL)
RSP = STACK_BASE + 0x80000 - 0x1000

# Map TLS & Stack Canary (FS Base)
FS_BASE = 0x800000
uc.mem_map(FS_BASE, 0x2000, UC_PROT_ALL)
uc.mem_write(FS_BASE + 0x28, struct.pack('<Q', 0x1122334455667788))
uc.msr_write(0xc0000100, FS_BASE) # Set IA32_FS_BASE MSR

6.3 Neutralizing Anti-Analysis via PLT Interception

By placing a single code hook across the PLT address range (0x404640 to 0x404720), we intercept every libc call:

def hook_plt(uc, address, size, user_data):
    rel = address - BASE
    rsp = uc.reg_read(UC_X86_REG_RSP)
    ret_addr = struct.unpack('<Q', uc.mem_read(rsp, 8))[0]
    uc.reg_write(UC_X86_REG_RSP, rsp + 8)
    uc.reg_write(UC_X86_REG_RIP, ret_addr)

    if rel in (0x4640, 0x4650, 0x46b0): # __cxa_finalize, close
        uc.reg_write(UC_X86_REG_RAX, 0)
    elif rel in (0x4660, 0x4670, 0x46e0): # fopen, fgets, fread
        uc.reg_write(UC_X86_REG_RAX, 0) # Return NULL: /proc files 'do not exist'
    elif rel in (0x4690, 0x46a0): # socket, connect
        uc.reg_write(UC_X86_REG_RAX, 0xFFFFFFFFFFFFFFFF) # Return -1: ports closed
    elif rel in (0x46c0, 0x4710): # memcpy, __memcpy_chk
        dst = uc.reg_read(UC_X86_REG_RDI)
        src = uc.reg_read(UC_X86_REG_RSI)
        n = uc.reg_read(UC_X86_REG_RDX)
        uc.mem_write(dst, bytes(uc.mem_read(src, n)))
        uc.reg_write(UC_X86_REG_RAX, dst)
    elif rel == 0x4700: # memset
        dst = uc.reg_read(UC_X86_REG_RDI)
        val = uc.reg_read(UC_X86_REG_RSI) & 0xff
        n = uc.reg_read(UC_X86_REG_RDX)
        uc.mem_write(dst, bytes([val] * n))
        uc.reg_write(UC_X86_REG_RAX, dst)
    elif rel == 0x46f0: # flag_commit
        rdi = uc.reg_read(UC_X86_REG_RDI)
        esi = uc.reg_read(UC_X86_REG_RSI)
        captured['flag'] = bytes(uc.mem_read(rdi, esi)).decode('ascii')

Because fopen and connect return failure, the application concludes that no debugger or Frida server is present, leaving [0xc960] == 0.

8. Key Takeaways & Educational Lessons

  1. Modern .NET Android Assembly Packing (XABA):
    • Reverse engineers targeting Android apps built with .NET 6/7/8/9 MAUI must look beyond conventional assets/assemblies/ folders.
    • Assemblies are embedded in the payload section of libassemblies.<arch>.blob.so using the XABA container format.
  2. Layered Decoys & Anti-Analysis:
    • Static string searches are defeated by synthetic decoy generators (DecoyFlagGenerator).
    • Anti-instrumentation sentinels (0xc960) silently corrupt cryptographic states rather than crashing immediately.
  3. Hybrid Cross-Boundary Architectures:
    • Modern CTF challenges increasingly distribute cryptographic operations across runtime boundaries (C# managed runtime $\leftrightarrow$ Native C ELF $\leftrightarrow$ Custom Bytecode VM).
  4. Power of CPU Emulation:
    • Instead of struggling with complex multi-architecture Android emulators and Frida bypass scripts, native libraries can be loaded and executed directly via Unicorn, providing total visibility and determinism.
